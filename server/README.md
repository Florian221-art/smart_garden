# Smart Garden – Server

Python backend for the Smart Garden planter, running on a Raspberry Pi 5. It

- receives sensor readings from the ESP32 planter (`POST /api/v1/readings`),
  authenticated with a per-device API key,
- stores them in a local SQLite database,
- answers each reading with the device configuration, pending one-time
  commands and the current demo-mode state (the ESP32 only makes outgoing
  requests, so everything the server wants the device to do travels back in
  this response),
- provides the read and control endpoints used by the React dashboard
  (`web/`), and
- serves the built dashboard (`web/dist/`) under `/` when it exists, so no
  separate web server is needed on the Pi.

The ESP32 waters the plant on its own, even when the server is unreachable;
the server supplies thresholds and can trigger manual actions.

The interface between the ESP32 and the server is defined in
`.claude/api-contract.md` (version 1.2).

## Tech stack

- FastAPI + uvicorn
- Pydantic v2 for request validation
- SQLAlchemy 2 with SQLite (WAL mode, foreign keys enabled)
- argon2 (`argon2-cffi`) for hashing API keys

Exact versions are pinned in `requirements.txt`. The deployment script
requires Python 3.10 or newer.

## Running locally

From the `server/` folder:

```
python3 -m venv .venv
./.venv/bin/pip install -r requirements.txt

# Register a device; the API key is printed once in plain text
./.venv/bin/python -m app.cli create-device esp32-kuebel-01

# Start the development server on http://127.0.0.1:8000
./.venv/bin/uvicorn app.main:app --reload
```

The tables are created automatically on startup (there is no migration tool).
The interactive API documentation generated by FastAPI is available at
`http://127.0.0.1:8000/docs`.

To test without hardware:

- `python tools/fake_esp.py --url http://127.0.0.1:8000 --key <api-key>`
  (from the repository root) sends simulated readings like the ESP32 does.
- `python -m app.dev_seed esp32-kuebel-01 --hours 48` fills the database with
  48 hours of simulated history (day/night cycle, drying soil with automatic
  watering, tank consumption, a short demo window and a DHT sensor failure),
  so the dashboard charts have data. It creates the device if it is missing.
  **Development only** – do not run it against the real database on the Pi.

On a Mac, `deploy/start-dashboard.command` does all of this (virtual
environment, test data for an empty database, backend and dashboard) in one
step. For deployment on the Raspberry Pi, see `deploy/README.md`.

## Configuration

Configuration is read from environment variables:

| Variable | Default | Purpose |
| --- | --- | --- |
| `SMART_GARDEN_DB_URL` | `sqlite:///<server>/smart_garden.db` | SQLAlchemy database URL |
| `SMART_GARDEN_WEB_DIST` | `<repo>/web/dist` | Folder of the built dashboard served under `/` |
| `SMART_GARDEN_RATE_LIMIT_S` | `2.0` | Minimum interval in seconds between two readings of the same device |

The default device configuration sent to the ESP32 (from `app/config.py`,
matching the API contract) is:

| Field | Default |
| --- | --- |
| `interval_s` | 15 |
| `moisture_min_pct` | 30 |
| `moisture_target_pct` | 55 |
| `auto_water` | true |
| `max_pump_s_per_run` | 5 |
| `pump_cooldown_s` | 300 |
| `max_pump_s_per_day` | 60 |
| `buzzer_enabled` | true |
| `tank_capacity_ml` | 1500 |
| `pump_flow_ml_per_s` | 20 |
| `tank_low_pct` | 20 |

These values are stored per device in the `device_config` table when a device
is created. There is no endpoint to change them yet.

## Device management (CLI)

Run from `server/` with the virtual environment:

| Command | Purpose |
| --- | --- |
| `python -m app.cli create-device <id> [--label ...]` | Create a new device and print its API key once |
| `python -m app.cli issue-key <id> [--label ...]` | Create the device if needed, otherwise replace its API key; prints only the key (used by `deploy/install_pi.sh`). Readings and configuration are kept |
| `python -m app.cli has-device <id>` | Exit code 0 if the device exists, 1 otherwise |

Device IDs must match `^[a-z0-9-]{1,32}$`.

## Authentication and security

- **ESP32 → server:** `POST /api/v1/readings` requires the header
  `X-API-Key`. Keys are generated with `secrets.token_urlsafe(32)` and only
  their argon2 hash is stored; verification uses argon2 (constant-time
  comparison). A missing or wrong key, or an unknown device, returns 401
  `{"ok": false, "error": "unauthorized"}`.
- **Rate limit:** at most one reading per device every 2 s (configurable);
  otherwise 429 `{"ok": false, "error": "rate_limited"}`. The limiter is in
  memory and therefore assumes a single server process.
- **Dashboard endpoints:** there is **no login or admin role yet**. All
  `/api/v1/devices/...` endpoints, including demo mode and device commands,
  are open to anyone who can reach the server (on the Pi: anyone on the
  "SmartGarden" hotspot). Every demo or command change is logged with the
  client IP address in the server log. The pump stays protected regardless:
  the server caps manual pump runs at `max_pump_s_per_run`, and the ESP32
  enforces its own hard limits for run time, cooldown and daily maximum.

## API endpoints

All timestamps are returned as ISO 8601 in UTC with a `Z` suffix.

### ESP32

| Method | Path | Description |
| --- | --- | --- |
| `POST` | `/api/v1/readings` | Submit a reading (requires `X-API-Key`) |

The request body contains `device_id`, `fw_version`, `seq`, `uptime_s`,
`rssi_dbm`, the sensor values (`soil_moisture_pct`, `soil_moisture_raw`,
`light_pct`, `light_raw`, `air_temp_c`, `air_humidity_pct`; each may be
`null` if the sensor failed), the watering state (`tank_remaining_ml`,
`water_level_pct`, `pump_on_s_since_last`, `pump_running`,
`auto_water_triggered`), `errors` and `demo_overrides`. Unknown fields are
rejected. `received_at` is set by the server. See the API contract for field
details.

A successful response looks like this:

```json
{
  "ok": true,
  "commands": { "pump_run_s": 0, "buzzer": false, "identify": false, "tank_refilled": false },
  "config": { "interval_s": 15, "moisture_min_pct": 30, "...": "..." },
  "demo": null
}
```

Pending commands are delivered exactly once and then cleared. `demo` is
`null` when demo mode is off, otherwise
`{"expires_in_s": ..., "overrides": {...}, "force_errors": [...]}`.

### Dashboard

| Method | Path | Description |
| --- | --- | --- |
| `GET` | `/healthz` | Liveness check, returns `{"ok": true}` |
| `GET` | `/api/v1/devices/{id}/latest` | Most recent reading of a device (404 if the device is unknown or has no readings yet) |
| `GET` | `/api/v1/devices/{id}/readings?from=&to=&bucket=` | History aggregated into time buckets (see below) |
| `GET` | `/api/v1/devices/{id}/config` | Current device configuration |
| `GET` | `/api/v1/devices/{id}/demo` | Current demo-mode state |
| `PUT` | `/api/v1/devices/{id}/demo` | Start or replace demo mode |
| `DELETE` | `/api/v1/devices/{id}/demo` | End demo mode immediately |
| `GET` | `/api/v1/devices/{id}/commands` | Commands not yet delivered to the ESP32 |
| `POST` | `/api/v1/devices/{id}/commands` | Queue one-time commands for the ESP32 |

**History** (`/readings`): `from` and `to` are ISO 8601 timestamps (default:
the last 24 hours); the range may be at most 31 days. `bucket` is the bucket
size in seconds; if omitted, the server picks a "round" size (15 s to 6 h)
that yields about 120 points, and at most 2000 points are allowed. Each point
contains the averages of soil moisture, light, temperature, air humidity,
water level, tank volume and RSSI, plus the total pump run time, the
estimated water usage (`water_ml` = pump seconds × `pump_flow_ml_per_s`), the
number of automatic watering events, a `demo` flag and the error codes seen
in that bucket. The response also includes the device configuration.

**Demo mode** (`PUT .../demo`): body
`{"overrides": {...}, "force_errors": [...], "duration_s": 120, "scenario": "..."}`.
Allowed overrides and ranges: `soil_moisture_pct` 0–100, `light_pct` 0–100,
`air_temp_c` -20–60, `air_humidity_pct` 0–100, `water_level_pct` 0–100.
Allowed forced errors: `dht_read_failed`, `soil_out_of_range`,
`light_read_failed`. `duration_s` is 10–600 (default 120). At least one
override or forced error is required. The ESP32 picks up the demo state with
its next reading and applies the values on the device itself, so the real
pump, LED bar and buzzer react.

**Commands** (`POST .../commands`): body with any of `pump_run_s` (> 0, ≤ 60,
capped by the server at `max_pump_s_per_run`), `tank_refilled`, `identify`,
`buzzer`. At least one command is required.

Invalid request bodies are rejected with status 422 (FastAPI's standard
validation response).

## Data storage

SQLite database (`smart_garden.db` in `server/` by default; on the Pi
`/opt/smart-garden/server/smart_garden.db`). Database files are excluded from
Git. Tables:

| Table | Content |
| --- | --- |
| `devices` | Device ID, argon2 hash of the API key, label, creation time |
| `readings` | Every received reading with all contract fields, including raw values, RSSI, uptime, errors and demo overrides |
| `device_config` | Configuration per device (see defaults above) |
| `pending_commands` | One-time commands waiting to be delivered to the ESP32 |
| `demo_state` | Active demo mode per device (overrides, forced errors, scenario, start and expiry time); expired entries are removed automatically |

| `app/routers/readings.py` | `POST /readings`, `GET .../latest` |
| `app/routers/history.py` | `GET .../readings`, `GET .../config` |
| `app/routers/control.py` | Demo mode and device commands |
| `app/cli.py` | Device management CLI |
| `app/dev_seed.py` | Simulated history for development |
